LA-004

Session Expiry

Functional High Partial

Precondition

User logged in, inactivity timeout configured (e.g. 15 min)

Steps

Expected result

Session is invalidated; user is redirected to the login screen.

Curl — prove the gap (run right after the UI redirects you to login)

# 1. Before idling, grab the token from your login response or devtools
# 2. After the UI kicks you to /auth/login, replay that same token directly:
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5000/api/v1/auth/me \
  -H "Authorization: Bearer <the old token>"
# A genuinely revoked session would return 401. It will return 200.
Reality A real per-role inactivity timer exists client-side (System Admin / Security Officer: 15 min; other roles vary) and will redirect you to the login screen — that part should genuinely pass in the browser. But it only clears local browser state; it never calls the logout endpoint, so the underlying token stays valid server-side until its fixed 15-minute lifetime runs out on its own. A captured token can still be replayed after the UI "logs you out."

LA-005

Forgot Password

Functional High Partial

Precondition

User has a registered email/phone

Steps

Expected result

Reset link is single-use, expires after a set time, and the new password logs the user in successfully.

Curl — request + reset + replay

curl -s -X POST http://localhost:5000/api/v1/auth/forgot/password \
  -H "Content-Type: application/json" \
  -d '{"email":"guardian@sims.edu.lk"}'
# find the reset link/hash wherever this dev environment delivers mail
curl -s -X POST http://localhost:5000/api/v1/auth/reset/password \
  -H "Content-Type: application/json" \
  -d '{"hash":"<hash from the link>","password":"NewPass123!"}'
# now replay the SAME hash again — a truly single-use link would reject this
curl -s -X POST http://localhost:5000/api/v1/auth/reset/password \
  -H "Content-Type: application/json" \
  -d '{"hash":"<same hash>","password":"AnotherPass456!"}'
Reality The endpoints are real and the link genuinely expires after 30 minutes. Two things won't match the spec: the same link can be replayed more than once inside that window (not single-use), and resetting does not log you in — you have to log in again afterward with the new password (it also force-logs-out every other active session on that account, which is good practice but not "auto-login").

LA-007

Invalid Credentials

Negative Medium Partial

Precondition

N/A

Steps

Expected result

A generic error is shown (no hint whether the email exists); account lockout/backoff triggers per policy.

Curl — confirm no lockout ever triggers

for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w "attempt $i -> %{http_code}\n" \
    -X POST http://localhost:5000/api/v1/auth/email/login \
    -H "Content-Type: application/json" \
    -d '{"email":"admin@sims.edu.lk","password":"wrong-password"}'
done
Reality The error message is close to generic but technically distinguishes "no such account" from "wrong password" under the hood — worth a note if you're being strict about enumeration. More importantly: there is no lockout or backoff of any kind anywhere in the backend. Every attempt above will return the same status code with no increasing delay and no eventual block. Given this case is flagged Critical in your test doc, recommend prioritizing this one on the backlog.

LA-008 / LA-009

Cross-Role Privilege Escalation

Security Critical Pass

Precondition

Logged in as a low-privilege role (e.g. Student)

Steps

Expected result

Request is rejected with 403/redirect; no data leaked.

Curl — API layer

# log in as a non-admin, e.g. teacher2@gmail.com, grab its token, then:
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5000/api/v1/users \
  -H "Authorization: Bearer <non-admin token>"
# expect 403 — not 200 with a user list

Browser — URL layer

While logged in as anything other than Principal, type /principal directly into the address bar. Expect a redirect to /403 or your own home dashboard — the Principal page should never render.

Reality Both layers are real and consistently applied: role-gated API guards on dozens of endpoints (the guard runs before the handler, so nothing leaks even transiently), plus route-level middleware and a page-level guard on the frontend as defense in depth.

Backlog — not fixed this pass

Reported as findings per your call; these are real features to build, not quick fixes, so they were left alone this round.

  1. MFA / OTP (LA-002, LA-003). No server-side MFA exists for any role. The frontend UI for it is already built and just needs a real backend counterpart (an OTP secret + verify endpoint + a "pending" token state on login).
  2. Login lockout / backoff (LA-007). No rate-limiting or attempt-counting exists anywhere on the login route. Worth adding given this case is rated Critical.
  3. Single-use password reset (LA-005). The reset token is a stateless signed link with no revocation store — needs either a one-time-use flag or moving off a pure JWT.
  4. Auto-login after password reset (LA-005). Currently the reset endpoint force-logs-out every session and returns nothing; a decision is needed on whether "logs the user in" should override that.
  5. Open question, not a bug: the backend has a bare user role (id 2) with no matching frontend dashboard and no seeded account. Worth confirming whether that role is ever meant to reach the login screen at all, or is purely an internal/system default.
